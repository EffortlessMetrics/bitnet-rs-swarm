# Support Triage Guide

Use this guide when a BitNet-rs command produces a surprising answer, a failed
validation, an unexpected backend, or a receipt that does not support the claim
you expected.

Start with the source-of-truth commands:

```powershell
bitnet model status --format json
bitnet receipts explain --latest --format json
bitnet support bundle --latest --format json
```

For a device-specific report, pass the exact device label:

```powershell
bitnet model status --device <device> --format json
bitnet support bundle --latest --device <device> --format json
```

The model status output says what the repository currently supports. The
receipt says what actually ran. The support bundle combines both for an issue.

## What To Paste In An Issue

Prefer the full `bitnet support bundle --latest --format json` output. If that
fails, paste the `bitnet receipts explain --latest --format json` output plus:

```text
bitnet version
operating system and CPU
GPU or accelerator, if requested
model id and artifact path or checksum
requested backend
selected_backend
selected_route
fallback_used
quality_gate
speedup_claim
server_ready
server_ready_scope
bitnet_packed_i2s_qk256_proof
dense_regular_llm_cuda_proof
receipt path
claim_boundary
next_proof
```

Do not paste tokens, credentials, private paths, model files, or unrelated logs.

## If `fallback_used=true`

Treat the run as diagnostic unless the support matrix for that exact path says
fallback is expected. A strict supported path should make fallback visible and
should fail closed when fallback would change the claim.

Check:

- the requested backend;
- the selected backend;
- the selected route;
- the fallback reason, if recorded;
- whether strict mode was requested;
- whether unsupported operation counts are present.

Allowed claim: fallback evidence for debugging.

Not allowed: supported answer readiness, CUDA execution, speedup, server
readiness, or BitNet QK256 proof for that run.

## If The Selected Backend Is Wrong

Backend labels are claim boundaries. For example, `cuda` is not the same claim
as `nvidia-rtx-5070-ti-cuda`, and `apple-m4-metal` is not the same claim as
`apple-m4-cpu-neon`.

Check:

- `requested_backend`;
- `selected_backend`;
- `runtime_api`;
- `selected_route`;
- the model coverage row for that device;
- the device matrix linked from [../status/SUPPORT_MATRIX.md](../status/SUPPORT_MATRIX.md).

Allowed claim: backend selection bug or ambiguous backend identity.

Not allowed: exact-device support, full residency, speedup, or server readiness
unless the receipt and support matrix name the exact device/profile.

## If Tokenizer Or Prompt Authority Is Missing

Artifact loading is not answer readiness. A model can be structurally valid but
still fail local-answer support if tokenizer or prompt-template authority is
missing.

Check:

- tokenizer source and checksum, if recorded;
- prompt template or prompt authority;
- stop-token policy;
- model coverage `next_proof`;
- whether the receipt was generated by `verify`, `ask`, `chat`, or a diagnostic
  command.

Allowed claim: structural validation or diagnostic loading evidence.

Not allowed: coherent local answer support, benchmark quality, or server
readiness.

## If The Quality Gate Failed

A failed quality gate is useful evidence, but it is failure evidence. Do not
promote support from it.

Check:

- `quality_gate` in the support bundle summary;
- answer, benchmark, or parity quality fields in the receipt explanation;
- prompt text and template family;
- first generated token or first divergence, if recorded;
- model/device row `next_proof`.

Allowed claim: reproducible quality failure with a receipt.

Not allowed: supported answer path, release readiness, or benchmark-qualified
speed.

## If `speedup_claim=false`

`speedup_claim=false` is normally correct unless an exact benchmark-qualified
receipt and support row promote speed for the same model, device, route, and
profile.

Check:

- `speedup_claim`;
- `benchmark_qualified_speedup`;
- accepted and blocked benchmark profiles, if present;
- selected backend and route;
- fallback state;
- device-specific capability matrix.

Allowed claim: execution happened, if the receipt proves execution.

Not allowed: speedup, performance superiority, full residency, or production
performance readiness.

## If `server_ready=false`

CLI readiness is not server readiness. Server readiness is exact-profile only
and must be promoted by the support matrix or device matrix for that model,
device, route, endpoint, and streaming mode.

Check:

- `server_ready`;
- `server_ready_scope`;
- `server_endpoint`;
- `server_streaming`;
- `server_smoke`;
- response quality gate;
- model/device/profile identity.

Allowed claim: server smoke or server diagnostic evidence.

Not allowed: broad OpenAI-compatible server support, broad dense model serving,
BitNet serving, or release server readiness.

## Dense Proof Versus BitNet Proof

Dense SLM proof and BitNet QK256 proof do not inherit from each other.

Use these fields to keep the boundary clear:

- `dense_regular_llm_cuda_proof`;
- `bitnet_packed_i2s_qk256_proof`;
- model coverage row;
- selected route;
- artifact family;
- tokenizer and prompt authority.

Allowed claim: the proof family named by the receipt and support matrix.

Not allowed: using Qwen2.5, Qwen3, SmolLM2, Llama, or other dense-model proof
as BitNet proof; using BitNet QK256 proof as dense-model proof.
